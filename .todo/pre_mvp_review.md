### 💡 [NEW-1] AI-Animated Hero Background — "Best View" Visualization

**Idea:** Replace the static hero `<Image>` with an AI-generated animated visualization of the property's best view — a living, breathing cinematic backdrop that no OTA listing page can replicate.

**Why this matters for hosts:**
- It's a unique, premium differentiator that's genuinely hard to replicate on Airbnb/Booking.com
- Transforms the hero from a static photo into a dynamic brand statement
- Gives hosts a compelling, tangible reason to choose our service over DIY website builders
- The "AI did this for your property" narrative is an excellent sales hook

**Open questions to resolve:**
- **Generation approach:** Pre-generate a short looping animation/video at onboarding time and store as a `.webm`/`.mp4` asset? Or use a runtime approach (CSS animation on the image + parallax)? Full AI video generation (Runway, Sora, Kling) vs. subtle CSS-based Ken Burns effect as MVP shortcut?
- **MVP shortcut option:** CSS `animation: kenBurns` (slow zoom + pan) on the existing hero image gives a 90% of the "alive" feeling with zero AI infrastructure. Could be the v0 while real AI video gen is built out.
- **Data model change:** `Property.heroVideo?: string` field for the generated clip URL.
- **Fallback:** Static image when no animation asset is available.
- **Performance:** Autoplay, muted, loop `<video>` replaces `<Image>`. Must not block LCP (largest contentful paint). `poster` attribute = first frame for instant display.

**Recommended path for MVP:** Ken Burns CSS animation → post-MVP swap in actual AI-generated video clip per property.

### 💡 [NEW-2] Payment Methods — Rethinking the Strategy

**Core philosophy:** Stay entirely out of the money flow. The product's value proposition is *zero cost to the host* — becoming a payment processor (even via Stripe) introduces liability, compliance (PCI-DSS, KYC, AML), payout logic, dispute handling, and fee extraction that directly contradicts the "cost-free" promise.

**Proposed approach — Contactless Handoff Model:**
The platform facilitates the *booking intent* but the actual payment happens directly between guest and host through a method they already trust.

**Payment method options to present in the mock and eventually in production:**

| Method | Host effort | Guest effort | Platform involvement | Recommended? |
|--------|-------------|--------------|---------------------|--------------|
| **Bank Transfer / IBAN** | Share IBAN once | Make a wire | Zero — platform shows IBAN | ✅ Yes — direct, free, universal in EU |
| **PayPal Friends & Family** | Share handle | Tap in app | Zero | ✅ Good for demos, no fees |
| **Revolut / Wise link** | Share payment link | Click & pay | Zero | ✅ Modern, low friction |
| **Crypto (USDC/USDT)** | Share wallet | Send stablecoin | Zero | 🟡 Niche, but no-fee angle is strong |
| **Cash / In-Person** | Arrange on call | Pay on arrival | Zero | 🟡 Supported as fallback |
| ~~Credit Card via Stripe~~ | ~~Stripe onboarding~~ | ~~Fill card details~~ | ~~Platform processes + takes cut~~ | ❌ Contradicts cost-free model |
| ~~Apple Pay / Google Pay~~ | ~~Stripe dependency~~ | ~~Tap~~ | ~~Platform is merchant of record~~ | ❌ Requires processor |

**What the "Book Direct" flow should actually do:**
1. Guest selects dates, sees transparent price breakdown
2. Presses "Reserve" — triggers a **booking intent form** (name, email, optional message)
3. System displays the host's preferred payment method(s) with instructions
4. Host is notified (email/WhatsApp/SMS) with guest details
5. Host confirms manually or via a simple one-click approve link
6. Guest gets a "pending confirmation" state, then "confirmed" on host approval

**Open questions:**
- Which methods to show in the mock demo for maximum credibility?
- Should the platform offer an optional "booking deposit" concept (e.g. guest sends 20% upfront via IBAN to secure dates)?
- Is there a future monetization angle in optional add-on services (upsell: professional AI video generation, custom domain, email templates) without touching payments?

**Recommended mock update:** Replace "Credit Card" + "Apple Pay" + "Instant Wire" with "Bank Transfer", "Revolut/PayPal", and "On Arrival" — with a text field for host's payment details. This is honest and aligns with the eventual real product.

**Future vision (Phase 2+):** User types *"I want a silent forest cabin with a sauna, 2 hours from Berlin, pet-friendly, for a 3-night digital detox"* → system matches against attribute index and returns ranked properties.

**Attribute taxonomy (proposed initial set):**

```
VIBE / MOOD
  [ ] Romantic  [ ] Family  [ ] Solo retreat  [ ] Digital detox  [ ] Adventure base
  [ ] Work remotely  [ ] Group celebration  [ ] Wellness & spa

SETTING
  [ ] Forest  [ ] Mountain  [ ] Lakeside  [ ] Oceanfront  [ ] Fjord  [ ] Desert
  [ ] Urban  [ ] Countryside  [ ] Island  [ ] Vineyard

PROPERTY TYPE
  [ ] Cabin  [ ] Chalet  [ ] Treehouse  [ ] Glass house  [ ] Loft  [ ] Villa
  [ ] Farmhouse  [ ] Lighthouse  [ ] Yurt  [ ] Floating home

SIGNATURE FEATURES (host-selectable)

  [ ] EV charging  [ ] Chef kitchen  [ ] Concierge breakfast
  [ ] Stargazing deck  [ ] Outdoor cinema  [ ] Private beach

AI-RECOGNIZED (from images + description)
  • Dominant color palette (warm/cool/neutral)
  • Architecture style (Scandinavian / Alpine / Mediterranean / etc.)
  • Light quality (bright & airy / moody & dark / golden hour)
  • Crowd estimate capacity
  • Proximity keywords from description ("minutes from", "walking distance")
```

**Data model change needed:**

```typescript
// Addition to Property interface
export interface PropertyAttributes {
  vibes: string[];            // host-selected from taxonomy
  setting: string[];          // host-selected
  propertyType: string;       // single canonical type
  signatureFeatures: string[]; // host-selected
```

**Open questions:**
- Who runs the AI tagging? On upload/onboarding via a background job? Or on-demand?
- What's the minimum viable attribute set for the discovery feature to be useful?
- Should `amenities: string[]` in the current model be migrated into this taxonomy, or kept separate?
- Privacy: Some AI-inferred attributes (e.g. "appears rustic / budget") could be sensitive — host approval flow before publishing AI tags?

### 💡 [NEW-4] Location Map Integration

**Feature:** Add an embedded location map at the bottom of each property page + a subtle "View Location" link on the hero photo (alongside the existing "View Spaces & Photos" button).

**Hero photo change:** Add a third pill/button in the top-right area:
```
[View Spaces & Photos ↓]  [View on Map ↓]
```
Both anchor-scroll to their respective sections.

**Map options (no API key required for MVP):**

| Option | Privacy | Setup | Accuracy control |
|--------|---------|-------|-----------------|
| **OpenStreetMap embed (iframe)** | Good — no Google tracking | Zero — just an iframe | Host sets approximate coords |
| **Google Maps embed** | Poor — tracks users | Zero for basic embed | Precise |
| **Mapbox GL JS** | Good | API key needed | Full control |
| **Leaflet.js + OSM tiles** | Excellent | No API key | Full control, open source |

**Privacy consideration:** Exact address should NOT be shown — hosts share approximate location (neighborhood/village level) to prevent guests from bypassing the booking. Show a pin with a blurred radius circle (like Airbnb does).

**Data model change needed:**

```typescript
// Addition to Property interface
export interface PropertyLocation {
  lat: number;
  lng: number;
  approximate?: boolean; // if true, jitter the pin slightly
  regionLabel?: string;  // e.g. "Lofoten Islands, Northern Norway"
}
```

**Current `Property.location` field** is just a string (e.g. `"Lofoten, Norway"`). Needs to be extended with coordinates.

**Recommended MVP approach:**
- Leaflet.js + OpenStreetMap (no API key, no tracking, open source)
- Approximate pin only — show a 2km radius circle instead of exact marker
- Simple React component `<PropertyMap lat={} lng={} label={} />`
- On the hero: add a small map-pin icon button linking to `#map` anchor

**Open questions:**
- Should coordinates be stored in the existing `location` field (structured) or as a separate `coordinates` field?
- Approximate-only or let host toggle exact address reveal after booking confirmation?
- Which map library — Leaflet (no key) or Mapbox (better styling, needs key)?

### 💡 [NEW-5] Brand Naming Brainstorm

**Context:** The current working name "bookuj" is a placeholder. We need a name that:
- Sells the *direct, fee-free, host-empowered* value proposition immediately
- Feels premium and trustworthy to boutique property hosts
- Works in English globally (even if the founding market is Polish)
- Is available as a `.com` or `.io` domain and not trademarked by a major OTA

**What the name should communicate:**
- *Direct* — bypassing OTAs, talking to the real host
- *Premium / boutique* — not budget, not mass market
- *Simple / transparent* — no hidden fees, no complexity
- *Ownership* — the host's own brand, their own channel

**Name directions to explore:**

```
DIRECTION 1 — "Direct" as core concept
  Directay, Direstay, Staydirect, Directhost, Folio (host folio)

DIRECTION 2 — "Own" / ownership angle
  Ownstay, Hosted.by, Herestay, Staywith.me

DIRECTION 3 — Boutique / concierge feel
  Retreatly, Sojourne, Hausstay, Sanctum, Atelier Stay

DIRECTION 4 — Compound / invented words
  Staylink, Locanda (Italian: inn), Feriare, Hostfolk, Conciergio

DIRECTION 5 — Direct fee-free angle
  Zeroway, Nocut, Freehost, Clearstay

DIRECTION 6 — Short, memorable, brand-able
  Kura, Nido (Italian: nest), Maho, Vela, Folium
```

**Criteria for final shortlist:**
1. ≤ 3 syllables ideally
2. `.com` available (check with Namecheap/Google Domains)

4. Easy to spell phonetically for non-English speakers

**Suggested session:** Run a naming sprint — generate 20+ candidates, score against criteria, check domain + trademark availability, shortlist to top 3, then host focus with a sample host persona.

## 🏗️ Architecture & Code Quality

### 🔴 Critical

#### 1. Template Duplication — `PropertyShowcaseTemplate` vs `DirectHostShowcase`
Two massive "full-page" components (~386 and ~515 lines) rendering nearly identical UIs (hero, calendar, price summary, payment modal, footer). The architecture docs describe **one universal template engine** but in reality there are two. This creates a painful maintenance burden — every fix or style tweak must be applied to both.

**Pre-MVP decision needed:** Which is the canonical template? `DirectHostShowcase` is significantly richer (OTA fee comparison, host recommendations section, editorial gallery captions). Is the plan to keep both long-term, or converge to one?

#### 2. Hardcoded Content in `DirectHostShowcase`
The `DirectHostShowcase` component is **not data-driven** for several sections:
- Gallery captions are hardcoded strings specific to Nordic Glass Sanctuary (`"The panoramic cedar sauna overlooking the fjord"`)
- The Host Recommendations section (Fjord Bakery, Eagle Ridge Trail, Hav Fishery Cellar) is entirely static copy
- The `/direct` route is **hardcoded** to `nordic-glass-sanctuary` slug

This directly contradicts the white-label architecture. If a host from Aspen, Colorado gets this template, they'll see a Norwegian fjord bakery recommendation.

#### 3. Modal State Not Reset on Property Switch
`PaymentModal` keeps `guestName` and `guestEmail` in local state seeded with `'Alexander Wright'` / `'alex.wright@example.com'`. When the property switcher navigates to a new slug, the modal state persists on the component. The booking reference is also generated with `Math.random()` on every render of the confirmed state, causing it to flicker on re-render. Use `useMemo` or `useId` for the reference number.

---

### 🟠 Significant

#### 4. Price Arithmetic is Inconsistent Between Templates
- `PropertyShowcaseTemplate`: Cleaning fee = `$0` ("Included"), `grandTotal = nights × pricePerNight`
- `DirectHostShowcase`: Cleaning fee = **`$60` flat** (hardcoded), `grandTotal = accommodationTotal + cleaningFee`
- `PaymentModal`: Cleaning fee ignored entirely, `grandTotal = nights × pricePerNight`

Three different price calculations for the same property shown to the same user. This is a conversion killer — the checkout modal will show a different total than what the booking summary card displayed.

#### 5. Currency Formatting — USD-Only `$` Sign Hardcoded
The `Property` type supports `'USD' | 'EUR' | 'GBP' | 'PLN'` but everywhere prices are rendered as `$XXX` with a hardcoded dollar sign. A PLN or EUR property will show `$450 PLN` which is broken. Need a `formatCurrency(amount, currency)` util.

#### 6. Calendar Doesn't Validate Range Against Occupied Dates
The `isDateDisabled` function disables individual occupied dates, but if a user selects a check-in and check-out range that **spans across** a blocked date, nothing prevents it. `react-day-picker` allows this by default unless you explicitly validate the full range on selection.

#### 7. `PropertyShowcaseTemplate` is a Client Component Unnecessarily
`PropertyShowcaseTemplate` is marked `'use client'` and takes `allProperties` as a prop (passed from the server page). Since `allProperties` is only used by the `PropertySwitcher`, this forces the entire page tree to become a client component. The `PropertySwitcher` could be isolated and the template could be a server component with just the interactive parts (`BookingCalendar`, `PaymentModal`, `PropertySwitcher`) being client components.

---

### 🟡 Minor / Polish

#### 8. Missing Minimum Stay Enforcement
The calendar legend says "2 nights minimum recommended" but there's no actual enforcement. A user can select 1 night and proceed to checkout. For MVP demo quality, this should either be enforced (disable same-day check-out) or the copy should be removed.

#### 9. `BookingCard.tsx` Exists But Is Not Used
The architecture docs reference `src/components/BookingCard.tsx` (7643 bytes) but neither page template imports it. Dead code or an abandoned approach.

#### 10. `HeroGallery.tsx` Exists But Is Not Used
Similarly, `HeroGallery.tsx` is defined in the architecture but the templates use inline `Image` components and ad-hoc grid markup instead. The component is imported in the architecture doc but not in either template.

#### 11. `lib/utils.ts` — Referenced in Architecture, Missing from Filesystem
The architecture lists `src/lib/utils.ts` with `clsx`/`tailwind-merge` helpers but the file may not exist (the data layer file only has `properties.ts`). `clsx` and `tailwind-merge` are both in `package.json` as dependencies.

#### 12. Static Meta Description in Root Layout
The root `layout.tsx` metadata title `"Book Direct - Boutique Direct Booking Platform"` is generic and doesn't reflect the demo context. The `demo/[slug]/page.tsx` correctly generates per-property metadata, but the root `/` page uses `'Direct Booking Concierge - Showcase'` which is inconsistent.

#### 13. Dark Mode CSS Conflict
`globals.css` has a `@media (prefers-color-scheme: dark)` block that sets dark background/foreground, but the theme engine sets `backgroundColor` via inline styles which will override this — creating an inconsistent experience for users who prefer dark mode.

## 🎨 UX & Conversion

#### 14. No Mobile Sticky CTA Bar
The PRD explicitly specifies "ergonomic sticky bottom CTA bar on mobile viewports." The `PropertyShowcaseTemplate` has no mobile sticky bar — the Book Direct button is only inside the calendar section, requiring the user to scroll down. The `DirectHostShowcase` also lacks this. On mobile, the primary conversion action is buried.

#### 15. Payment Modal — Pre-filled Guest Info Feels Like a Bug
Users who open the modal will see it pre-filled with "Alexander Wright" / "alex.wright@example.com". Prospective hosts demoing this to clients will find it jarring. The demo data should either be clearly labeled as a demo placeholder or cleared on modal open.

#### 16. No Empty State for Properties with No Images
If `property.images[1]` doesn't exist (e.g. a property with only 1 image), the "View Spaces & Photos" button thumbnail will break with a 404, and the gallery grid will show empty cells.

#### 17. `PropertySwitcher` Overlaps Mobile Booking CTA
The switcher is fixed at `bottom-20 lg:bottom-6` which accounts for a sticky CTA bar that doesn't actually exist. On mobile, it floats in the middle of the viewport's lower quarter with nothing to avoid.

---

## 🔒 Demo Safety / Presentation Risk

#### 18. "Instant Wire Transfer" Option in Mock Checkout
Offering "Instant Wire Transfer" as a payment option — even in a mock — might confuse prospective hosts into thinking this is how direct booking payments work. It's a high-commitment payment method. Consider renaming or replacing with "Bank Transfer / IBAN" to be more realistic.

#### 19. Booking Reference Number Flickers on Re-render
```tsx
#DIR-{Math.floor(100000 + Math.random() * 900000)}
```
This generates a new random reference on every render cycle of the confirmed state, which can cause visible flickering during the fade-in animation. Wrap in `useMemo` with an empty dep array.

#### 20. The `/direct` Route Is Not Linked From Anywhere
`/direct` exists as a dedicated page but the `PropertySwitcher` only links to `/demo/[slug]`. Stakeholders reviewing the demo won't discover the enhanced `DirectHostShowcase` layout unless they know the URL. Consider adding a toggle in the `PropertySwitcher` or documenting it.
